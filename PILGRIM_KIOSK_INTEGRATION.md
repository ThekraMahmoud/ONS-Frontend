# ONS Pilgrim Kiosk integration checklist

The kiosk uses the existing read-only device list API for its test selector. The backend was inspected but not changed. This checklist describes the Spring backend in `IdeaProjects/ONS`.

## A. Implemented and verified

- `/pilgrim-kiosk` is a separate React Router route. `/pilgrim-kiosk/setup` is the separate device-testing selector. The selected device ID is kept in tab-scoped `sessionStorage`, then resolved again from the real device list. `/` remains `HomePage`; the kiosk has no link in campaign navigation.
- The clean full-screen kiosk is `/pilgrim-kiosk`; append `?preview=device` for a separate physical-terminal frame preview. The frame is outside the kiosk application and includes a direct link back to the clean display.
- Full-screen, touch-oriented kiosk layout with welcome/language selection, a three-service menu, assistance method choice, and localized unavailability/retry screens.
- The separate setup route calls existing `GET /api/v1/kiosks/get`, supports searching by real kiosk code/location, displays available location/city/status fields, handles loading/error/empty/no-match states, and lets the operator select/switch the simulated device. The selected ID is tab-scoped and re-resolved from the API; it is not device authentication. The last successful API response contained active device `KIOSK-005` at `Main Entrance`; the backend was unavailable during the latest route check.
- Welcome uses the original ONS logo and exact official wording “لكم من القلب، أنس ومن الاهتمام”, a native-language/flag grid, browser speech synthesis, and a larger-text accessibility toggle. Camera access requires HTTPS or localhost and browser permission. Audio output requires supported browser speech synthesis and an enabled speaker; native translations still need professional review.
- QR selection opens a live rear-camera-preferred preview using `getUserMedia`. Where the browser supports `BarcodeDetector`, it reads QR values locally into in-memory state; the value is not sent to the backend and is never described as verified. Camera permission, unavailable-device, busy-camera, insecure-context, and decoder-support states have retry/cancel UI.
- Manual entry calls existing `GET /api/v1/pilgrims/get/{id}` with a positive numeric database ID. The new `PilgrimResponseDTO` returns `fullName`, `nationality`, `phoneNumber`, `visaNumber`, `campaignId`, and `campaignName`; the kiosk shows name, nationality, a masked visa number, and campaign name. Record retrieval and user confirmation are not identity verification. Report submission uses the DTO's `campaignId`; the pilgrim never selects a campaign.
- Locale strings are organized in `src/i18n/kioskLocales.js` for Arabic, English, Urdu, Indonesian, Bengali, Turkish, Persian, French, Hausa, Russian, Simplified Chinese, Swahili, and Amharic. Arabic, Urdu, and Persian use RTL; the other listed locales use LTR. Every locale has screen labels, privacy notices, and honest pending states. All non-Arabic translations need qualified native review before production; the Amharic and Hausa copy especially needs review.
- City-specific photography is selected from explicit Makkah/Madinah location names or coordinates within 60 km of the corresponding city center. Unknown locations do not silently default to either city.
- The current frontend has no kiosk-management screen. The backend exposes existing manual device creation at `POST /api/v1/kiosks/add`; use the project's established admin workflow to add devices. If the API list is empty, the selector explains that no records were found and offers retry; it never displays mock devices.
- `Kiosk` contains `kioskCode`, `locationName`, required latitude/longitude, status, heartbeat, and a reverse one-to-many reports relation. It has no campaign or zone relation. The selected device ID is retained in component state but cannot determine a campaign, zone, or responsible team from this model.
- QR values are not sent to the server. Manual entry sends only a numeric database ID to the existing pilgrim-by-ID endpoint and is explicitly labeled as an unverified record lookup. Returned details remain in transient component state until reset/navigation. After the user confirms the displayed record, the kiosk submits an assistance report using the existing report endpoint and the DTO's linked campaign ID. No phone GPS is requested, and no unverified nearby location/distance/route is displayed.
- Two photographs from Wikimedia Commons are bundled with source/license details in `src/assets/images/KIOSK_PHOTO_CREDITS.md`.

## B. UI implemented, backend/device integration pending

### Existing devices, device context, and location trust

- **Existing backend:** `GET /api/v1/kiosks/get` returns manually registered `Kiosk` records; `GET /api/v1/kiosks/get/{id}` returns one. The frontend selector calls the list endpoint. The last successful response returned one active device; the backend was stopped/unreachable during the latest checks.
- **Exact relationship gap:** `Kiosk` has no campaign or zone foreign key. `AssistanceReport` relates independently to a kiosk and campaign; the kiosk does not identify which campaign/zone should receive its report. `Accommodation` has campaign/city but no zone. There is no `Zone` entity in this backend.
- **Security gap:** `Configuration.java` permits every request via `.anyRequest().permitAll()`. The selector is a demonstration tool, not proof of physical device identity and not authorization for report creation.
- To route production reports by selected device, the backend needs a persisted and validated kiosk-to-operational-context relationship (campaign and zone or an equivalent responsible-team relationship), plus a protected device context endpoint. GPS is not required for manual selection, but the model currently marks latitude and longitude non-null.

### Pilgrim identity and QR verification

- **Existing backend:** `GET /api/v1/pilgrim-cards/get/{id}` takes a numeric database ID (not a documented QR token or card number). `PilgrimCard` stores a card number but has no verification/QR token, and its pilgrim relation is ignored in JSON. `GET /api/v1/pilgrims/get/{id}` retrieves a database record; it is not identity verification and returns full name, nationality, phone, and visa number. The UI uses that endpoint only for a clearly labeled lookup and renders name/nationality only. There is no safe card-number lookup contract, QR credential field, or kiosk verification endpoint.
- **Security gap:** The global `permitAll()` rule makes those lookup endpoints anonymously enumerable. They can expose personal/card data and cannot safely be used by a public kiosk. Do not deploy the manual lookup publicly until the endpoint is protected or replaced with a secure verification contract.
- **Needed capability:** A kiosk-authenticated, rate-limited endpoint, e.g. `POST /api/v1/kiosk/identity/verify` with `{ deviceCredential, method: "QR" | "MANUAL", qrToken? , documentType?, documentNumber? }`. Return only `{ verified, verificationToken?, pilgrim?: { displayName, maskedDocument, campaignDisplayName? }, reason?: "NOT_FOUND" | "INVALID" }`. Use a signed/opaque, revocable QR credential, short-lived verification token, throttling, and privacy-safe logs. The camera UI is implemented with browser `BarcodeDetector` where supported; unsupported browsers show the live preview with an explicit decoder message.

### Nearby restroom/gate discovery and directions

- **Existing backend:** `GET /api/v1/routes?startLon&startLat&endLon&endLat` delegates to public OSRM driving directions, but requires destination coordinates. There is no restroom/gate inventory or nearby-search endpoint. Accommodation data is not a restroom/gate directory.
- **Needed capability:** Maintain verified, localized restroom/gate destinations and expose a kiosk-context query such as `GET /api/v1/kiosk/nearby?type=RESTROOM|GATE` → `{ items: [{ id, localizedName, latitude, longitude, directionText?, distanceMeters? }] }`. Return only destinations appropriate for the registered site and operating context. Confirm route mode and indoor/precinct coverage before using OSRM or another routing service.
- The current UI explains that directions are unavailable; it never uses the pilgrim's device location or invents destinations/distances.

### Report persistence, routing, and tracking

- **Existing backend:** `POST /report/add` accepts an `AssistanceReport` entity with `pilgrim: { id }`, `kiosk: { id }`, `campaign: { id }`, and a unique, non-null `caseNumber`; it resolves the three IDs, forces `OPEN`, saves, and returns only a generic success message. The kiosk reads the campaign ID from the pilgrim API response, creates a unique case number in the browser because the backend does not generate one, and shows the saved state/reference only after the POST succeeds. The backend does not return the case number or provide a lookup-by-case-number tracking endpoint.
- **Assignment behavior:** Report creation does not assign or notify a supervisor/representative. A later staff `acceptPilgrim` operation sets `ASSIGNED` to whichever authorized-staff ID is sent; it checks report/pilgrim match and open status but not campaign, zone, or responsibility. The kiosk links a report to the selected campaign and device, but the current path does not route it to a responsible person or guarantee the correct team.
- **Security/model gaps:** The report and pilgrim/card routes are permitted anonymously; enumerating pilgrim IDs can expose personal data. The DTO exposes the required campaign ID without serializing the full entity relation. The UI does not guess the campaign or ask the pilgrim to choose one. The UI does not claim identity verification, assignment, or tracking.
- **Needed capability:** `POST /api/v1/kiosk/reports` authenticated by kiosk device credentials and bound to a short-lived verified identity token. Suggested request `{ verificationToken, category: "LOST_PILGRIM" }`; server resolves pilgrim, campaign, kiosk, location, zone, assignment, case number, status, and timestamp. Return `{ reportReference, trackingToken, status: "OPEN", createdAt }`. Persist report and assignment atomically; enforce existing campaign/zone/staff authorization.
- Add a secure, non-enumerable `GET /api/v1/kiosk/reports/{trackingToken}` returning only `{ reportReference, status, updatedAt }`. Permit only actual `ReportStatus` values and existing valid transitions; do not expose identity details.
- Safe identity verification, trusted device context, automatic campaign routing, server-side case-number generation, staff assignment/notification, and report tracking remain backend gaps. The existing report-creation endpoint is used as implemented; a successful POST is the only condition for showing the saved state.

## C. Not implemented

- Server-side QR verification, verified/unregistered/network identity outcomes, nearby-place results, secure report tracking, and zone-aware routing remain blocked on backend/device capabilities above. QR capture is frontend-only and browser-dependent. Report creation uses the existing `POST /report/add` endpoint with the campaign ID returned by `PilgrimResponseDTO`; identity lookup/report routes should not be publicly deployed while the backend allows anonymous enumeration.
- The page does not enforce an idle timeout. Home/start-over clears the current transient personal-data state; the selected kiosk ID persists only for the browser tab session.
- The bundled location photographs are genuine historical photos (Makkah 2007, Madinah 2010), not current live imagery. Check suitability/operational guidance before public deployment; credits and licenses are in `src/assets/images/KIOSK_PHOTO_CREDITS.md`.
- All translations other than Arabic are drafts and require professional native-language review before use in a public service terminal.
